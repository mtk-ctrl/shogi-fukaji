# 深路：継続実行・予約確認・再開（AI共通）

ChatGPT・Claude共通。製品名ではなく**長時間の自律実行、予約実行、通知、永続保存、再開**の実際に利用可能な能力で判断する。本人の「タイマー連鎖」要求（2026-10-30）は維持する。正式採用の委任ではない。

## 基本
読取・分析・設計・実装・短い検証は、同じ実行枠で結果を確認しながら続行する。commitや作業区切りだけを理由に後回しにしない。**実際に開始した**非同期runをその枠内で最後まで確認できないときだけ、run ID・開始時刻・進捗・完了条件を記録して単発の確認予約を使う。稼働runなし、本人判断待ち、安全停止なら予約を置かない。

## タイマー連鎖の定義
1. 次の具体的作業を実際に開始。
2. 同種実測・残量・queue・集計/保存に基づき、その作業の終了見込みを計算。
3. 同じ枠で完了確認できない外部runについて、利用可能な予約機能で終了見込みに対応する単発確認を設定。
4. 確認時に実結果と永続保存を読取り、次工程を開始。必要なら新しい見込みで単発予約を更新。

5分の作業を根拠なく1時間後の終了予定にしない。毎時/5分ごとの固定周期、実行中でない作業時間の見積りへの混入、予約制約を隠す時刻の水増しは禁止。予約できる時刻と終了見込みに差があれば、双方の時刻・差・機能制約を別々に記録。規則を迂回しない。

## 同等機能がないAIの代替
有限・明示起動のGitHub Actionsを使い、run ID・commit・計画SHA・結果・失敗をD系文書に記録。重い学習stateとoptimizerは本人限定Driveに保存し、owner-only・再取得SHA・実復元を検証。 `docs/decisions/` とD系へ次工程・再開条件・実行コマンドを残し、**次の対話**で別AIが読み直して再開する。予約実行や無人継続を実現したとは主張しない。

ローカル計算は同じ環境で完了と永続保存まで追う。別環境へは[D27](../D27_PORTABLE_RECOVERY_20261102.md)の停止確認・exclusive lock・state/archive一致・実復元を満たす `stopped_handoff` で引継ぐ。`recovery_checkpoint_only` は別writerの起動許可ではない。複数AIの同時書込みを禁止する。

## 確認・引継ぎ項目
| 状態 | 対応 |
|---|---|
| 短い作業やCIを今確認できる | 同じ枠で検査・保存・次工程 |
| 長い実runが稼働し今確認できない | run IDと終了見込みから単発予約（機能が使える場合のみ） |
| runはないが別の実作業は可能 | 予約なしで実行 |
| 環境喪失・安全拒否・本人判断待ち | 原因、保存済み証拠、停止範囲、再開条件を正本へ記録 |

引継ぎには実施済みcommit/run/成果、次作業・成功条件、作業状態、実run ID、終了見込みの根拠、予約実時刻、制約による差、同じ枠で続けられない理由を残す。登録成功/実発火/結果取得/次工程を分けて確認する。

## タイマー連鎖の完了ゲートと失敗時の処理（2026-11-08追記）

- **タイマー設定完了≠連鎖成功。** 予約IDが存在し有効なこと、予約実時刻、実発火、対象外部run全ページの結果取得、永続保存のSHA読戻し、事前基準による採否、次工程の実起動、次工程のETA算定、次の予約作成とそのID読戻しを段階ごとに証拠とともに記録する。
- 予約が発火した時点で対象runが稼働中なら、未完了を成果とみなさず、runner実測から残りを再計算し**次の単発確認を登録してから**終了する。予約を作れなかったなら理由と未接続状態を通知・正本記録する。
- 対象runが終了したら、原棋譜・model・optimizer・評価・全Release/コミットのSHAと事前採用条件を検証する。条件通過なら同じ枠内で正式採用CIと次世代1000局の実開始まで進める。次の長いrunが稼働したら、その終了見込みに合わせて単発を予約する。**次回やると書いただけ、結果を報告しただけでは連鎖継続ではない**。
- 実行環境に予約作成・GitHub書込みツールがない場合は、連鎖できないことを明示する。根拠のない時刻への予約や固定周期への置換、実際にはできていない後続工程の完了宣言は禁止する。
- 2026-11-08 D58の12:32 JST単発は発火したが進捗報告のみで次の単発予約を欠き、13:10 JSTの単発も完了記録に対してD59採用runを開始していなかった。単発の自動発火だけでは**永続的な無人継続が実証されていない**。[実例と是正記録](../decisions/2026-11-08_D59採用_D60起動_タイマー連鎖の再設計.md)。次の検証ポイントはD60結果確認時の「次工程実起動＋次タイマー登録」。

## タイマーが途切れた根本原因と起動方法（2026-11-08 15:50是正）

- **実行経路の誤認が主因**：予約環境がGitHub Actionsの `workflow_dispatch` 操作を直接提供していなくても、対応するworkflowが `on.push.paths` で待ち受ける **`research/Dxx/START.json` の新規作成・更新をGitHubコネクタで行えばActionsを実起動できる**。既に会話上でD59/D60/D60回復をこの方法で実起動し、run IDを取得済み。予約側は「dispatch不可」と判断して修正・報告で終了し、この代替経路を使わなかった。次回の予約本文には最初から対象のworkflowファイル・`START.json` 路径・期待されるrun名・旧run IDを示す。
- **一度に仕事を詰めすぎた**：旧予約は「200局結果確認→新世代採用の新スクリプト4つ作成→1000局CI準備→起動→再予約」を一度に求め、後工程の実作業・再予約に達する前に短い報告で停止した。今後は**実際に稼働している一工程を完了確認→次の有限CIを実起動→そのrunに対する単発確認を作成**という短い単位を基本とする。単発の発火時刻までに作れるコード/CIは前もって作成しておく。複雑なコード修正や不具合の再検証は現在の実行枠で継続し、成功済みの1000局を再生成しない。
- **時計の扱い**：同種の200局評価はD58実測で `audit_prepare` 開始12:55:37 JST→`finish`終了13:04:35 JST、**8分58秒**。1000局＋学習の81分53秒を200局比較に流用してはならない。新200局評価の終了見込みは **audit_prepare→20ジョブ監査→finishの実測と各ジョブの経過** から計算し、数分の処理を根拠なく遠い予約にしない。予約サービスには指定時間より早く/遅く発火した実例があるので「scheduled_for」「started_at」を別々に照合する。
- **実行成功ゲート**：予約作成の前に (a) main HEAD、稼働run・競合、(b) workflowの`on.push.paths`、(c) `START.json`と実モデルSHA・元Release SHAの完全一致、(d) GitHub `create_file` または `update_file` 成功、(e) **GitHub Actions APIから新run ID・状態を実取得**を必須とする。GitHub dispatchツールだけが無いことを「Actions実行不可」と取り違えない。push以外にも本当に書込経路がない場合にのみその旨を停止理由にする。
- **予約更新ゲート**：次工程の実runが存在する場合、実測に即した終了見込みへ**新しい単発予約を実作成**し、予約ID・有効状態・予定時刻を読戻してGitHub正本へ記録する。作成失敗時はエラー、別環境の制約、状態を明示し、予約成功/次工程実行済みを主張しない。無制限のcron・無制限のGitHub Actions再起動は禁止（F30）。
- **予約環境の失敗は実測**：12:32のD58確認は進捗報告だけ、13:10は発火後D59起動無し、15:10のD60確認はコード修正だけで200局再実行・再予約無し。いずれも予約自体は発火した。**先に時刻を置くことより、後続起動経路を実装/検証しなかったことが連鎖断絶の直接原因**。改修の検証は「次工程のGitHub実runが作られ、さらに次の単発予約も有効」の両方を同一回で確認したときのみ成功とする。
