# 深路の継続実行とタイマー

対象は深路だけ。R00/R21の安全・権限・重複防止を維持し、本人の「終了見込みに合わせて次の仕事へつなぐ」という意図を実際に使える機能の範囲で扱う。2026-10-30の本人の「修正して下さい」に基づく。研究候補の正式採用委任ではない。

## 最優先：タイマーを使う条件
本人の2026-10-30の訂正：「GitHub Actions等のランナーを走らせて待ちが発生する作業ではタイマー連鎖が必要。待ちがない作業は、このChatGPT WORKで深路を強化する大目標のもと継続する」。

**通常の読取・分析・設計・実装・短い検証はWORK内で続ける。** 作業の区切りや実行頻度制約を理由に、未着手の仕事を次回起動へ送らない。

タイマーを有効化・再予約するのは、実際に開始した非同期処理（ランナー等）を、同じ作業ターンで最後まで確認できない場合。対象run ID・進捗・完了条件・終了見込みの根拠を保存する。同じターンで結果まで確認できる短いCI等は、その場で確認する。

稼働する待ち対象がないなら、予約を作らず作業を続ける。安全拒否・本人判断待ちは、時間経過で完了するバックグラウンド処理ではない。許可された別作業を進め、本当に継続不能なときは具体的な障害として報告する。「研究Goal未達だから再開枠を残す」をタイマー作成の理由にしない。誤って置いた予約の停止は研究Goalの完了を意味しない。

## 0. 本人が指定する「タイマー連鎖」の定義
1. 次の具体的な作業を実際に開始する。
2. その作業の進捗・実測を根拠に終了予定時刻を見積もり、その時刻を対象とする単発の確認予約を設定する。
3. 予約で再開したら実際の結果を確認し、その結果から次の作業を決めて実行する。
4. 新しい作業について改めて終了予定時刻を見積もり、同じ単発タスクを更新する。これを繰り返す。

各回の時刻は作業ごとに決まる。本人は「5分ごと」「毎時」等の固定間隔の定期実行を求めていない。「タイマー連鎖」という指示だけから、一定の短周期実行や制限回避の要求へ読み替えない。短い作業を同じターンで処理する方法は、その場で完了できる場合の実行上の補助であり、この定義を別方式へ置き換えるものではない。

本人の要求と、利用機能が許す実行頻度は別に確認する。「単発だから頻度制約を常に受けない」とも、「短い工程を含むから方式全体が実現不能」とも断定しない。実際に希望する終了予定と利用規則が衝突する場合は、その具体的な予約の制約として明示し、禁止される呼出しは行わない。予約可能時刻を終了予定時刻へ読み替えない。

## 0.1. 今回までの本人指示をまとめた必須原則
- 次の作業をAIが具体化して実際に動かし、その作業の終了見込みに単発確認を置く。予約で結果を確認し、次の作業を動かして、その新しい終了見込みへ同じ単発タスクを更新する。
- 毎回の予約時刻は作業ごとに決める。固定の5分ごと・毎時の定期実行を求められたと読み替えない。
- **5分で終わる見込みの作業を、根拠なく1時間後に確認する予約へ延ばさない。** 予約しやすい時刻、きりのよい時刻、前回と同じ間隔、AIの都合は終了見込みの算定根拠にならない。
- 同種の実測・開始時刻・残量・実在するbuild/queue/集計/成果物保存を根拠に、結果を確認できる時刻を算定する。処理が5分でも実測の後処理に別の時間が必要なら、その内訳を示す。無根拠な大幅余裕を付けない。
- まだ動かしていない計算・未着手の比較を、実行中の作業の所要時間や終了見込みへ足し込まない。「約5分の実作業」と「54分後の予約」を同じ意味で説明しない。
- その場で完了・確認できる短い作業は、そのまま次へ進む。完了報告・PR統合・記録保存だけで打ち切って、次の予約まで空白を作らない。早く終わった場合も同じ。
- 予約機能の具体的制約は、実作業の見積もりと分ける。希望の時刻が登録不能なら、規則やエラーの対象を特定して報告する。勝手に一時間後へ変更して「終了予定」と呼ばない。禁止された呼出しや制限回避は行わない。
- 登録成功、有効表示、実際の起動、実際の結果取得、次工程の開始を区別する。保存・起動・検証をしていないものを完了としない。
- 同じ説明を本人にやり直させない。継続案件の開始・タイマー更新・自動再開でAGENTS→ルーター→本Rule→対象実験と直近メモリを読み、会話での訂正を適用する。記録したことを全チャットの自動同期保証とは説明しない。

### 予約更新直前の点検
1. その作業は実際に動いているか。run/開始時刻/現在の進捗があるか。
2. 終了見込みの根拠は何か。処理・queue・後処理の内訳は妥当か。
3. 設定する時刻はその見込みと合っているか。5分見込みを一時間へ伸ばす等の不一致を見逃していないか。
4. 機能制約で時刻が違うなら、終了見込み・実登録時刻・差・制約の証拠を分けたか。
5. 今このまま進められる作業を、予約待ちへ送ろうとしていないか。

## 1. 一回の起動で行うこと
実作業→短い検証→結果から判断→次の実作業、を同じ作業ターン内で続ける。小工程一つの完了、PRの統合、記録保存、次工程の計画だけでは、継続研究を終了して予約待ちにする理由にならない。

- 毎回、ルーター・必要なRule・現在の実験文書・Addnessの直近メモリ・実際のGitHub状態を確認する。
- 実行可能な次工程があればその場で着手する。短いCIもその場で結果まで追跡する。
- 次工程は現在の結果と未解決点から選ぶ。過去の文書の「次はD1/D2」や古いタスクの説明を、完了済み工程を再実行する根拠にしない。
- 終了するのは、本人の停止地点、本人判断待ち、解消できない具体的な実行制約、または同じターンで完了確認できない実在の外部処理待ち等がある場合。続けられる別作業の有無も確認する。
- 一時間を埋めるための再測定・無意味な検査・待機・sleepはしない。実行時間の下限や工程数ノルマを作らない。
- 拒否された操作を同じ結果に至る別経路で迂回しない。保存拒否と研究自体の不具合を分け、許可された独立作業だけを進める。

## 2. 予約の前に状態を分類する
| 現在の状態 | 行動 |
|---|---|
| 次の短い実作業を実行できる | 同じターンで実行。工程完了を理由に次回へ送らない |
| 短いCI・集計が稼働中で、その場で確認できる | 同じターンで結果確認し、次へ進む |
| 実際の長時間処理が稼働し、その場で完了確認できない | run IDと進捗から終了見込みを計算し、提供機能で許された時刻に同一タスクを一回限り更新 |
| 稼働する非同期処理がなく、読取・分析・設計・実装を進められる | タイマーを置かずWORK内で続行。未起動作業の終了見込みへ予約しない |
| 同じ安全拒否・本人判断待ちで、条件が変わっていない | 同じ操作を反復しない。停止した対象と再開条件を保存し、許可された独立作業の可否を判断 |

「次回は予約できる最短時刻だから一時間後」は、作業時間の見積もりではない。未起動の計算が待機中にも進んでいるように報告しない。実作業の見込みが短いからといって、利用規則に反する短周期の自動再開を登録しない。

## 3. 見積もりと引継ぎに必須の項目
次の予約へ渡すときは、タスク本文に下記を残す。未確認は未確認、不明な時間は不明とし、数字を埋めない。

1. 完了済みの実作業と証拠（commit、run、結果の所在）。
2. 次の具体的な実作業と成功条件。
3. 作業状態：未着手／準備中／実行中／完了／障害中。
4. 待ち対象：実run IDまたは具体的な制約。稼働処理がなければ「なし」。
5. 作業終了見込み：工程別の最近の同種実測、残量、queue、後処理による算定。未起動・見積不能ならその旨。
6. 次回再開時刻：実際に登録した時刻と根拠。終了見込みより遅い場合は、その差と理由。
7. 同じターンで続けられなかった具体的な理由。単に「工程が終わった」「保存した」では不足。

作業終了見込みと次回再開時刻を同じフィールドにまとめない。暫定見積もりを実測と呼ばない。早く終わったら次の実作業へ進み、予約時刻まで空白を作らない。

## 4. 提供機能の制約
- 現在接続しているAutomationsの呼出規則は、一時間に一回を超える頻度の自動実行を禁止している。利用規則で禁止される頻度に当たる再実行を、単発という形式・別ID・run_now・外部からの自己呼出しで回避しない。本人の工程別の単発予約更新という目的自体を、制限回避の指示とみなさない。
- 公式文書には同じチャットの分単位再開機能があるが、今回の接続からの利用・動作は未確認。切替済みとは報告しない。
- 運用を修正したことと、短周期の自動再開という機能上の不足が解消したことを分ける。
- 同一の一回限りのタスクを使用する。今回の修正で毎時のRRULEや新しいタスクを追加しない。
- 自動再開が提供制約で遅れるなら、制約と空白時間を明示する。見積もりを水増しして隠さない。

## 5. GitHubの実状態を確認する
正規のread-only GitHub接続で、対象repoの以下を取得する。
- Actions実run一覧：`GET /repos/{owner}/{repo}/actions/runs`
- runのjobs：`GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs`

コミットのrun取得ツールがPRイベント限定なら、mainのpush CIが見つからないことを接続全体の取得不能としない。空のcombined statusも成功とは扱わない。これは取得対象の合う通常の読取機能を選ぶ手順であり、認可拒否・安全拒否を迂回する許可ではない。エラー時は対象・時刻・呼出経路・原文を保存する。重い実測の起動前には、既存の全repo確認・空きrunner・同目的重複等の条件を引き続き満たす。

## 6. 検証と報告
設定保存（prompt/時刻/有効状態の読戻し）、実発火（対象run IDと開始時刻）、実作業、完了・保存、次工程の実行を別々に確認する。古いlatest_resultを新しいrunの結果と混同しない。in_progressだけからworkerの稼働を断定しない。

ユーザー向けには「変更した設定」「実測できた行動」「未検証」「残る機能制約」を区別する。予約の読戻しだけで本人が意図するタイマー連鎖の完全修復とは報告しない。
