# 深路の継続実行とタイマー

対象は深路だけ。R00/R21の安全・権限・重複防止を維持し、本人の「終了見込みに合わせて次の仕事へつなぐ」という意図を実際に使える機能の範囲で扱う。2026-10-30の本人の「修正して下さい」に基づく。研究候補の正式採用委任ではない。

## 1. 一回の起動で行うこと
実作業→短い検証→結果から判断→次の実作業、を同じ作業ターン内で続ける。小工程一つの完了、PRの統合、記録保存、次工程の計画だけでは、継続研究を終了して予約待ちにする理由にならない。

- 毎回、ルーター・必要なRule・現在の実験文書・Addnessの直近メモリ・実際のGitHub状態を確認する。
- 実行可能な次工程があればその場で着手する。短いCIもその場で結果まで追跡する。
- 次工程は現在の結果と未解決点から選ぶ。過去の文書の「次はD1/D2」や古いタスクの説明を、完了済み工程を再実行する根拠にしない。
- 終了するのは、本人の停止地点、本人判断待ち、解消できない具体的な実行制約、または同じターンで完了確認できない実在の外部処理待ち等がある場合。続けられる別作業の有無も確認する。
- 一時間を埋めるための再測定・無意味な検査・待機・sleepはしない。実行時間の下限や工程数ノルマを作らない。
- 拒否された操作を同じ結果に至る別経路で迂回しない。保存拒否と研究自体の不具合を分け、許可された独立作業だけを進める。

## 2. 予約の前に状態を分類する
| 現在の状態 | 行動 |
|---|---|
| 次の短い実作業を実行できる | 同じターンで実行。工程完了を理由に次回へ送らない |
| 短いCI・集計が稼働中で、その場で確認できる | 同じターンで結果確認し、次へ進む |
| 実際の長時間処理が稼働し、その場で完了確認できない | run IDと進捗から終了見込みを計算し、提供機能で許された時刻に同一タスクを一回限り更新 |
| 未起動・予約間隔・実行枠等の制約で再開待ち | 作業終了見込みは未設定。待ち理由と次回再開時刻を分けて保存。可能な別作業を先に実行 |
| 同じ安全拒否・本人判断待ちで、条件が変わっていない | 同じ操作を反復しない。停止した対象と再開条件を保存し、許可された独立作業の可否を判断 |

「次回は予約できる最短時刻だから一時間後」は、作業時間の見積もりではない。未起動の計算が待機中にも進んでいるように報告しない。実作業の見込みが短いからといって、利用規則に反する短周期の自動再開を登録しない。

## 3. 見積もりと引継ぎに必須の項目
次の予約へ渡すときは、タスク本文に下記を残す。未確認は未確認、不明な時間は不明とし、数字を埋めない。

1. 完了済みの実作業と証拠（commit、run、結果の所在）。
2. 次の具体的な実作業と成功条件。
3. 作業状態：未着手／準備中／実行中／完了／障害中。
4. 待ち対象：実run IDまたは具体的な制約。稼働処理がなければ「なし」。
5. 作業終了見込み：工程別の最近の同種実測、残量、queue、後処理による算定。未起動・見積不能ならその旨。
6. 次回再開時刻：実際に登録した時刻と根拠。終了見込みより遅い場合は、その差と理由。
7. 同じターンで続けられなかった具体的な理由。単に「工程が終わった」「保存した」では不足。

作業終了見込みと次回再開時刻を同じフィールドにまとめない。暫定見積もりを実測と呼ばない。早く終わったら次の実作業へ進み、予約時刻まで空白を作らない。

## 4. 提供機能の制約
- 現在接続しているAutomationsの呼出規則は、一時間に一回を超える頻度の自動実行を禁止している。単発予定の連発、別ID、run_now、外部からの自己呼出しで回避しない。
- 公式文書には同じチャットの分単位再開機能があるが、今回の接続からの利用・動作は未確認。切替済みとは報告しない。
- 運用を修正したことと、短周期の自動再開という機能上の不足が解消したことを分ける。
- 同一の一回限りのタスクを使用する。今回の修正で毎時のRRULEや新しいタスクを追加しない。
- 自動再開が提供制約で遅れるなら、制約と空白時間を明示する。見積もりを水増しして隠さない。

## 5. GitHubの実状態を確認する
正規のread-only GitHub接続で、対象repoの以下を取得する。
- Actions実run一覧：`GET /repos/{owner}/{repo}/actions/runs`
- runのjobs：`GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs`

コミットのrun取得ツールがPRイベント限定なら、mainのpush CIが見つからないことを接続全体の取得不能としない。空のcombined statusも成功とは扱わない。これは取得対象の合う通常の読取機能を選ぶ手順であり、認可拒否・安全拒否を迂回する許可ではない。エラー時は対象・時刻・呼出経路・原文を保存する。重い実測の起動前には、既存の全repo確認・空きrunner・同目的重複等の条件を引き続き満たす。

## 6. 検証と報告
設定保存（prompt/時刻/有効状態の読戻し）、実発火（対象run IDと開始時刻）、実作業、完了・保存、次工程の実行を別々に確認する。古いlatest_resultを新しいrunの結果と混同しない。in_progressだけからworkerの稼働を断定しない。

ユーザー向けには「変更した設定」「実測できた行動」「未検証」「残る機能制約」を区別する。予約の読戻しだけで本人が意図するタイマー連鎖の完全修復とは報告しない。
