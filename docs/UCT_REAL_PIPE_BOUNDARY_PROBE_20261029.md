# 深路UCT：限定サブプロセスと実パイプの境界検証（2026-10-29）

## 狙いと時計の境界

前段の[合成IPCモデル](UCT_SYNTHETIC_IPC_PROTOCOL_20261029.md)は実バイト送信・flush・子プロセス終了を検査していなかった。`fukaji/uct_pipe_probe.py`は標準ライブラリだけで、有限時間で終了する子を`Popen`で起動し、親の単調時計と実パイプからの非ブロッキング読取りで、改行区切りJSONの受信・断片化・重複・破損・遅延・旧世代・旧局面・異常終了を調べる。子はbufferの`flush()`を明示する。

- 親の`time.monotonic_ns()`を基準に、**実際に親が最後のバイトを読んだ時点**で期限前か判定する。子が申告する時刻は使わない。最初のバイト観測時刻と行完成時刻は異なるため、前者だけを受信完了としない。
- 親のstopは**観測フラグ**であり、子への停止信号・強制終了・正式USI `stop` ではない。期限後/stop後の行は候補として採用せず、事前に渡した合法手snapshotの先頭をfallbackとして保持する。合法手の真正性は既存の履歴付きpython-shogi snapshot側の責務であり、このプローブ自身は将棋ルールを証明しない。
- 子は固定モードのみ。`Popen(shell=False)`で単一子を起動、標準入力なし、出力上限4096バイト、最大10秒の明示待ち、テストでは3秒。正常・異常終了とも`wait`で回収し、パイプを閉じる。子が想定外に残存した場合は成功を偽装せず失敗を報告し、別run/他のrunnerは停止しない。
- 送信バッファへの書込みと`flush`、親のpipe読取り、親の候補受理、`bestmove`の正式stdout送信、GUIの受信確認、ワーカーの完全資源解放は**すべて異なる**。この試験で確認できるのは親pipe読取り・子終了・親が所有するパイプのcloseまで。GUI受信と200ms硬い保証を主張しない。
- 既存の`SyntheticIpcModel`と正式USIにはまだ配線しない。二重応答防止や連続goの合成モデルの成功と、実I/Oの到達性を混同しない。

## 軽量テストと残課題

`tests/test_uct_pipe_probe.py`は11件。通常のflush済み1行、分割行の再構成、旧世代、旧局面、JSON破損、改行欠落、重複行、子異常終了、遅延の親時計拒否、stop先行、未知モード・不正引数拒否を検査する。CI負荷による処理時刻の変動を避けるため、正常受理試験の時間予算は2秒、遅延拒否は1msという十分に離れた条件で検査し、200msの実測値には転用しない。全ケースで有限時間の子だけを使い、OSの強制停止はしない。

次工程：実際の200ms応答設計では、`go`受信から合法手snapshot作成、IPC遅延、親の書込み/flush、USI送信完了までを計測し、子の異常・停止遅延・残留資源の管理方針を別途検証する。親監督がOSからスケジューリングされない場合、Pythonと通常OSで絶対期限を保証できない。研究正式採用、雲路main変更、未決着教師化はしない。
