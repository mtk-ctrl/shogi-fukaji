## 不具合と再発防止の具体策
1. 200局部分の実所要：D58は`audit_prepare` 12:55:37 JSTから`finish` 13:04:35 JSTの8分58秒。D60はaudit_prepare 15:44:25開始、実対局全20ランナー成功後の集計に旧schemaが残っていたため別集計runを要した。200局そのものに1000局＋学習の所要時間を適用しない。
2. **D60は2箇所のschemaハードコード漏れ**：prepareが最初はD60自身の形式を親D58に要求し、修正後はcollectが旧D58の計画形式をD60計画に要求。最終修正は[PR #170](https://github.com/mtk-ctrl/shogi-fukaji/pull/170)とfinish-only CI。集計CIが、producer/consumer双方が同じschema `d60-paired200-v1` を期待する静的契約検査を追加。保存済み全棋譜の利用を優先して再対局を防止。
3. **タイマー連鎖停止の直接原因**：単発発火後の実行環境は直接`workflow_dispatch` APIを提供しないことを、Actions実起動不能と取り違えた。現行workflowが監視する `on.push.paths` に合う `research/Dxx/START.json` を、GitHub connector `create_file` でmainへ追加すれば、実際にActionsを起動できる。会話中でD59、D60、D60 200局復旧および集計復旧を同経路で実証している。この**pushによる起動を優先し、必ず新run IDを取得**することを[F01](../rules/F01_継続実行とタイマー.md)へ明記。
4. **タイマーの報告完了は連鎖完了でない**。次のActions run ID取得と、次の単発予約のID・enabledを同じ回で読戻したときだけ連鎖成功とする。処理が未完了なら数分後の実測ETAへ単発再予約。未稼働の場合は空予約をしない。
5. 予定15:56→15:57 JSTへ更新した単発 `Automation_836d2858c20c819194dd4b11a589abc1` にD60結果確認→D61正式採用のGitHub実起動→次の単発予約までの短い手順を明記した。予約の実発火と連鎖成功は改めて確認が必要。
